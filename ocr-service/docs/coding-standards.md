# 项目规范

`ocr-service` 的目标不是承载业务流程，而是提供稳定、可复用、可替换的 OCR 能力。因此规范重点是分层边界、接口稳定性和输入安全。

## 一、分层约束

1. `app` 只负责路由、依赖装配和 HTTP 映射。
2. `providers` 只负责 OCR 引擎适配。
3. `services` 只负责 provider 无关的编排、输入加载和预处理。
4. `models` 只负责请求、响应和内部契约定义。
5. `config` 只负责配置读取和默认值定义。

禁止跨层越权：
- `app` 不直接调用 PaddleOCR
- `services` 不直接 import OCR SDK
- `providers` 不处理 HTTP 路由或 FastAPI 响应对象

## 二、Provider 规范

1. 任何 OCR SDK 只能出现在 `providers` 层。
2. Provider 必须实现稳定接口，不能把底层 SDK 对象直接暴露给上层。
3. Provider 失败时要抛出明确错误，不允许吞错后返回伪成功结果。
4. Provider 必须支持 mock 或 null 替身，便于单元测试。

## 三、接口规范

1. `/health` 必须轻量且无副作用。
2. 如果需要检查引擎是否可用，应单独设计 readiness 语义，不要让健康检查触发模型初始化或下载。
3. API 不能接受“传了但不生效”的参数。
4. 对尚未支持的参数，要么实现，要么显式拒绝。
5. 响应结构必须稳定，便于其它项目长期集成。

## 四、输入安全规范

1. 文件输入必须受 `allowed_roots` 约束。
2. base64 输入必须限制解码字节大小。
3. 图片加载前必须限制最大宽高和最大像素量。
4. 超限输入必须在进入 provider 前失败。
5. 超时控制必须配置化，不能无限等待 provider。

## 五、错误处理规范

1. 非法输入返回 `400`
2. 文件不存在返回 `404`
3. Provider 调用失败返回 `502`
4. 未预期异常返回 `500`

所有错误都应保留结构化日志，便于后续排查。

## 六、测试规范

1. 单元测试默认不依赖真实 Paddle 运行时。
2. 真实引擎验证放到独立集成测试，不阻塞基础单元测试。
3. 项目必须提供单命令可运行的测试入口。
4. 测试不得依赖工作区绝对路径和人工设置的临时 `PYTHONPATH`。

## 七、仓库卫生规范

以下内容不得提交：
- `__pycache__`
- `*.egg-info`
- `build`
- `dist`
- 运行日志
- 临时识别产物

`.gitignore` 必须始终覆盖这些生成物。

## 八、文档规范

README 至少要写清楚：
- 安装方式
- 启动命令
- 测试命令
- provider 切换方式
- 允许读取的路径边界

任何协作文档都必须保持可读编码，不能出现乱码文件进入共享基线。
